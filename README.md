> [!IMPORTANT]
> Спутник в зоне видимости ещё не означает, что связь есть. OrbitGuard считает
> доступность только тогда, когда в этот момент существует полный путь от
> клиентской площадки до работающего наземного шлюза.

## Зачем нужен OrbitGuard

Инженер загружает сценарий группировки, меняет конфигурацию и за несколько
секунд видит, выдержит ли сеть целевой SLA. Сервис моделирует топологию на всей
суточной сетке, строит маршрут для каждого клиента в каждый момент и объясняет
причину каждого разрыва.

| Вопрос инженера | Что даёт OrbitGuard |
|---|---|
| Хватит ли первой или второй очереди запуска? | Сравнение доступности и максимальных перерывов по этапам развёртывания |
| Что будет при отказе аппарата или шлюза? | Перестроение маршрутов, анализ критичности и единых точек отказа |
| Как выбрать ориентацию орбитальных плоскостей? | Изменение RAAN и фазирования, сохранение вариантов, оптимизатор |
| Почему в конкретный момент нет связи? | Одна из четырёх диагностик разрыва с отображением топологии |
| Повлияют ли здания, лес или рельеф? | Локальные маски горизонта и профили окружения наземных площадок |
| Можно ли проверить другой набор данных? | Импорт, полевая валидация и экспорт сценариев формата `cosmo-A-1.0` |

## Возможности

| 🗺️ Визуализация | 🧪 Что-if анализ | 📊 Результат |
|---|---|---|
| 3D-глобус и 2D-карта | Этапы развёртывания | Доступность каждого клиента |
| Динамические GSL/ISL-связи | RAAN и фазовый сдвиг плоскостей | Максимальный перерыв связи |
| Подсветка полного маршрута | Отказы спутников и шлюзов | Длина и состав маршрута |
| Таймлайн состояния за сутки | Рельеф и застройка площадок | Причина отсутствия пути |
| WebGL fallback на плоскую карту | Чувствительность к дальности ISL | Сравнение сохранённых вариантов |

Дополнительно доступны ранжирование спутников по ущербу от отказа,
автоматический поиск лучшего фазирования и выгрузка результата в официальном
формате `cosmo-A-result-1.0`.

## Как работает расчёт

```text
Сценарий cosmo-A-1.0
        │
        ▼
Валидация и применение конфигурации
        │
        ▼
Положение спутников на каждом t_s
        │
        ▼
Динамический граф GSL + ISL
        │
        ▼
Маршрут до любого доступного шлюза
  BFS: min_hops │ Dijkstra: min_distance
        │
        ▼
Доступность · перерывы · причины отказов · экспорт
```

Для официального суточного сценария это 720 состояний с шагом 120 секунд.
Каждое состояние рассчитывается заново: какие аппараты активны, какие наземные
и межспутниковые линии существуют и можно ли по ним дойти до шлюза. Клиентские
наземные пункты являются только конечными узлами и никогда не ретранслируют
чужой трафик.

Если пути нет, движок различает четыре причины:

- `no_visible_satellite` — клиент не видит ни одного спутника;
- `network_partition` — клиент подключён к изолированному фрагменту сети;
- `no_gateway_contact` — работающий шлюз не имеет связи со спутниками;
- `gateway_unavailable` — все шлюзы находятся в окне отказа.

## Эталонные результаты

Метрики ниже воспроизводятся на исходных сценариях из [`data/`](data) и
зафиксированы тестом
[`test_reference_metrics.py`](backend/tests/unit/test_reference_metrics.py).
Проценты здесь — только формат отображения; API передаёт доли от `0` до `1`.

| Сценарий | C65 | C70 | C72 | Максимальный перерыв C65 / C70 / C72 |
|---|---:|---:|---:|---:|
| `01_full_constellation` | **96,7%** | **98,8%** | **98,9%** | 8 / 2 / 2 мин |
| `02_first_launch` | 27,2% | 15,8% | 12,6% | 572 / 658 / 796 мин |
| `03_satellite_outages` | 79,3% | 80,8% | 82,5% | 24 / 24 / 20 мин |
| `04_link_range` | 77,5% | 62,2% | 65,1% | 94 / 178 / 4 мин |

Целевой уровень — **не менее 90% для каждого клиентского пункта**. Его выполняет
полная группировка; стресс-сценарии показывают, где именно архитектура теряет
устойчивость.

## Быстрый сценарий для демонстрации

1. Откройте [live-версию](https://orbitguard-frontend.vercel.app) и выберите
   `01_full_constellation`.
2. Перемещайте таймлайн: глобус покажет текущую топологию и полный маршрут до
   шлюза.
3. Переключите этап развёртывания с 3 на 1 — доступность клиентов упадёт с
   `96–99%` до `13–27%`.
4. Выберите спутник на активном маршруте и задайте ему окно отказа: сеть найдёт
   обход или покажет точную причину разрыва.
5. Измените RAAN или фазу плоскости, сохраните конфигурацию и сравните варианты
   бок о бок.
6. Запустите анализ устойчивости или оптимизатор, затем экспортируйте результат.
7. Импортируйте собственный JSON того же формата — идентификаторы, количество
   аппаратов, плоскостей, шлюзов и временной шаг берутся из файла, а не из
   встроенных констант.

## Быстрый запуск

### Требования

- Docker Engine с Docker Compose;
- Node.js 20+ и npm для интерфейса;
- для разработки backend без Docker: Python 3.13 и
  [`uv`](https://docs.astral.sh/uv/).

### 1. API, PostgreSQL и Redis

```bash
cp .env.example .env
docker compose up -d --build
```

Миграции применяются автоматически при старте контейнера. Четыре официальных
сценария из [`data/`](data) загружаются в каталог при первом запуске.

### 2. Интерфейс

```bash
cd frontend
cp .env.example .env.local
npm ci
npm run dev
```

| Сервис | Адрес |
|---|---|
| OrbitGuard | [http://localhost:3000](http://localhost:3000) |
| REST API | [http://localhost:8080](http://localhost:8080) |
| Swagger UI | [http://localhost:8080/api/docs](http://localhost:8080/api/docs) |
| ReDoc | [http://localhost:8080/api/redoc](http://localhost:8080/api/redoc) |
| Health check | [http://localhost:8080/api/health](http://localhost:8080/api/health) |

Остановить инфраструктуру:

```bash
docker compose down --remove-orphans
```

### Локальная разработка backend

```bash
make install                 # создать backend/.venv и установить зависимости
make test-up                 # PostgreSQL :55432 и Redis :56379 для разработки
make migrate                 # применить Alembic-миграции
make dev                     # API с hot reload на :8080
```

Frontend проксирует `/api/*` на `API_ORIGIN`, поэтому браузер работает с одним
origin. По умолчанию используется `http://localhost:8080`.

## API

Базовый префикс бизнес-методов — `/api/v1`. Авторизация намеренно отсутствует:
инструмент должен открываться для проверки без регистрации.

| Область | Основные методы |
|---|---|
| Сценарии | `GET /scenarios`, `POST /scenarios`, `POST /scenarios/upload`, `POST /scenarios/validate` |
| Симуляции | `POST /simulations`, `GET /simulations/{run_id}`, `/snapshot`, `/ephemeris`, `/availability`, `/routes/{client_id}` |
| Экспорт | `GET /simulations/{run_id}/export`, `GET /simulations/{run_id}/scenario` |
| Варианты | `POST /variants`, `GET /variants`, `POST /variants/compare` |
| Аналитика | `POST /analysis/resilience`, `POST /analysis/sensitivity`, `POST /analysis/optimize` |
| Задания оптимизатора | `GET /jobs/{job_id}`, `GET /jobs/{job_id}/result` |

Полная интерактивная схема доступна в [Swagger UI](https://orbitguard-backend.fly.dev/api/docs),
версионированный снимок — в [`docs/openapi.json`](docs/openapi.json), описание
контракта — в [`docs/API_CONTRACT.md`](docs/API_CONTRACT.md).

### Wire-конвенции

| Тип данных | Конвенция |
|---|---|
| Ключи | `snake_case` |
| Время | секунды от начала прогона, поле `t_s` |
| Углы | градусы |
| Расстояния | километры |
| Доступность и видимость | доля `0…1`, не процент |
| Длительность перерыва | секунды |
| Идентификаторы | без изменений из исходного сценария |

Ошибки предметной области возвращаются как документы
[RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html). Повторный запуск
одинакового эффективного сценария идемпотентен: `run_id` вычисляется из его
содержимого и стратегии маршрутизации.

## Архитектура

```text
frontend/  Next.js · React · TanStack Query · Three.js
    │
    ▼
api/v1/    тонкие FastAPI-роутеры: HTTP и валидация
    │
    ▼
service/   orchestration: сценарий → конфигурация → расчёт → хранение
    ├──────────────┬────────────────────┐
    ▼              ▼                    ▼
engine/         domain/              database/
чистый расчёт   Pydantic-контракт    PostgreSQL + Redis cache
```

Расчётный пакет [`backend/src/engine`](backend/src/engine) не зависит от
FastAPI, SQLAlchemy, Redis и сервисного слоя. Это позволяет запускать и
тестировать всю обязательную математику без инфраструктуры.

```text
backend/src/
├── api/v1/           REST API: scenarios, simulations, variants, analysis
├── service/          сценарии, прогоны, сравнение и задания оптимизатора
├── domain/           Pydantic-модели публичного контракта
├── database/         SQLAlchemy, Alembic, Unit of Work и Redis cache
├── engine/           geometry, routing, simulation, metrics, analysis
└── core/             конфигурация, middleware и RFC 9457 errors

frontend/src/
├── app/              Next.js App Router и глобальные провайдеры
├── views/            сборка рабочей студии
├── widgets/          глобус, таймлайн, панели анализа и сравнения
├── features/         настройки, отказы, оптимизатор, импорт и экспорт
├── entities/         scenario, simulation, satellite, site, variant
└── shared/           API-клиент, UI-примитивы, конфигурация и i18n
```

## Корректность и ограничения

- [`geometry.py`](backend/src/engine/geometry.py) скопирован из архива кейса
  байт-в-байт и защищён тестом контрольной суммы; изменять его нельзя.
- Референсные результаты четырёх сценариев являются контрактом с техническим
  жюри и проверяются автоматически.
- Клиентские площадки никогда не используются как промежуточные узлы маршрута.
- Окружение площадки может только удалить разрешённую геометрией наземную
  линию, но не создать новую.
- Идентификаторы и размеры группировки не зашиты в код: сервис принимает
  сценарии с другими координатами, количеством объектов и временным шагом.
- Redis используется только как cache: его отказ снижает скорость, но не
  делает API недоступным. PostgreSQL хранит сценарии, прогоны и варианты.

## Производительность

Измерения на официальной группировке из 48 аппаратов:

| Операция | Типичное время |
|---|---:|
| Полный суточный прогон, 720 состояний | ~0,15–0,24 с |
| Анализ критичности 48 спутников | ~2,3 с в process pool |
| Один coordinate descent, 3 свободные плоскости | ~17 с / 158 кандидатов |

Обычная симуляция синхронна. Только оптимизатор использует протокол фонового
задания. Тяжёлые артефакты — эфемериды, состояния сети и маршруты — выдаются
отдельными эндпоинтами и не раздувают основной ответ.
