# OrbitGuard — проектирование устойчивой спутниковой группировки

Веб-сервис для кейса КосмоХакатона 2026 «Проектирование устойчивой
спутниковой группировки». Инженер загружает сценарий группировки, меняет очередь
запуска, ориентацию и фазирование плоскостей, отказы аппаратов и окружение
наземных площадок, прогоняет сутки и видит, есть ли у каждого северного пункта
**сквозной маршрут до шлюза** в каждый момент времени — и где и почему его нет.

> Спутник над головой — это ещё не связь. Метрика — наличие непрерывной цепочки
> `клиент → спутник → … → спутник → шлюз` на каждом отсчёте расчётной сетки.

## Запуск с чистого клона

Нужны Docker и Node.js 20+. Бэкенд, Postgres и Redis поднимаются одной командой,
фронтенд — второй.

```bash
# 1. Бэкенд + БД + кеш (API на http://localhost:8080, документация на /api/docs)
cp .env.example .env
docker compose up -d --build

# 2. Фронтенд (http://localhost:3000, ходит в API через /api/* без CORS)
cd frontend
npm install
cp .env.example .env.local        # API_ORIGIN=http://localhost:8080 по умолчанию
npm run dev
```

Четыре официальных сценария из папки `data/` загружаются при старте бэкенда.
Разработка без Docker для бэкенда, тесты и линтеры — в [`Makefile`](Makefile)
(`make help`) и в [`backend/README.md`](backend/README.md).

```bash
make test-up && make migrate      # одноразовые postgres :55432 и redis :56379
make test                         # 84 теста: 63 юнит + 21 интеграционный
make test-unit                    # только движок, инфраструктура не нужна
```

## Демонстрационный сценарий, который можно повторить

Это те же «базовые сценарии проверки» из постановки задачи, в порядке защиты.

1. **Полная группировка.** Открыть сервис, в выпадающем списке выбрать
   `01_full_constellation`. Расчёт занимает ~0.15 с. В карточке «Состояние сети»
   слева вверху — доступность каждого пункта (96.7 / 98.8 / 98.9 %) и текущий
   маршрут; на глобусе — спутники, межспутниковые связи и маршруты всех трёх
   пунктов. Тянуть ползунок времени внизу — сеть перестраивается.
2. **Этап развёртывания.** В панели справа, группа «Развёртывание», переключить
   очередь 3 → 1. Доступность падает до 27 / 16 / 13 %, самая длинная дыра —
   13 часов. Полоски доступности под таймлайном показывают три состояния: есть
   маршрут / спутник виден, маршрута нет / спутника нет.
3. **Отказ аппарата.** Кликнуть спутник на маршруте (на глобусе или в списке
   «Спутники»), нажать «Отказ с {время}» — отказ начинается с текущего момента
   таймлайна и длится до конца суток. Маршрут перестраивается в обход, либо
   появляется перерыв с причиной (нет видимого спутника / разрыв межспутниковой
   сети / нет контакта со шлюзом / шлюз недоступен). Группа «Отказы» задаёт окно
   произвольно; группа «Простои шлюза» делает то же для шлюза.
4. **Изменение проекта.** В группе «Плоскости» поменять RAAN или фазу одной
   плоскости (0–360°, значение можно ввести с клавиатуры), нажать «Сохранить
   вариант», затем вернуть исходное и сохранить второй. Вкладка «Сравнение»
   показывает изменённые параметры, итоговые показатели по каждому пункту и
   рекомендацию.
5. **Окружение площадки** (расширение сверх кейса, запрошенное постановщиком).
   В группе «Наземные объекты» у шлюза `G_MUR` выбрать «ГОРОД»: все три пункта
   падают до ~46 %, потому что каждый маршрут заканчивается на шлюзе. Вернуть
   «ПОЛЕ», у клиента выбрать «ГОРОД» — падает только он. На глобусе штриховыми
   линиями показаны спутники, которые выше маски терминала, но скрыты застройкой.
6. **Загрузка своего файла.** Кнопка «ИМПОРТ» в шапке принимает файл формата
   `cosmo-A-1.0`; при ошибке сервис называет поле, которое надо исправить.
7. **Выгрузка.** «Экспорт» отдаёт `cosmo-A-result-1.0` (по одной записи на пару
   «момент × пункт», внутри — использованный сценарий); «Скачать итоговый
   сценарий» отдаёт файл, который можно загрузить обратно.

Дополнительно: вкладка «Устойчивость» ранжирует спутники по ущербу от их потери и
показывает зависимость от шлюза; кнопка «Оптимизировать группировку» подбирает RAAN и фазу
плоскостей покоординатным спуском (~17 с, 158 прогонов), любой угол можно
зафиксировать.

## Что моделируется, а что нет

Считается ровно то, что задано в «Описании данных»: круговые орбиты, сферическая
Земля, единая маска угла возвышения, межспутниковый контакт по дальности и
отсутствию пересечения с Землёй, сетка 720 отсчётов. Формулы и правила —
организаторов, файл `geometry.py` скопирован байт в байт.

Сверх кейса добавлено одно: **окружение наземной площадки**. У пункта может быть
профиль (поле, море, тайга, город, долина или своя маска), азимутальный профиль
горизонта и высота над сферой. Эффективная маска — максимум из маски сценария и
локальной, поэтому окружение только убирает связи и никогда не добавляет; при
нейтральном профиле цифры совпадают с эталонными до последнего знака (это
закреплено тестами). Пропускная способность, задержки, энергобаланс,
многолучёвость и надёжность аппаратов не моделируются — организаторы вывели их
за рамки кейса.
