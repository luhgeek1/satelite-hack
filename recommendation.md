# 1. Организаторы практически подарили половину спутникового кейса

Вот что уже есть.

Группировка:

* 48 спутников
* 3 орбитальные плоскости
* 3 очереди запуска по 16 аппаратов
* высота 550 км
* сутки моделирования
* шаг 120 секунд
* всего **720 временных состояний**

И главное, вам дали `geometry.py`, который уже умеет:

* валидировать JSON;
* считать координаты спутников;
* учитывать вращение Земли;
* учитывать RAAN;
* учитывать фазирование;
* вычислять видимость наземной станции;
* вычислять межспутниковые связи;
* учитывать дальность ISL;
* учитывать перекрытие Землёй;
* учитывать отказ спутника;
* учитывать отключение gateway.

То есть значительная часть страшной космической математики **уже написана организаторами**.

Ваша основная математика сверху:

```text
snapshot
   ↓
graph
   ↓
client → satellite → satellite → ... → gateway
   ↓
BFS / Dijkstra
   ↓
availability
max outage
route
reason of failure
```

Это вообще не aerospace research.

Это **обычная задача графов + аналитика + frontend**.

Claude/Codex такое едят прекрасно.

# 2. Я даже прогнал предоставленные сценарии

Я взял официальный `geometry.py` и поверх него сделал простейшую маршрутизацию по графу.

Получилась очень прикольная картина.

| Сценарий                 |       C65 |       C70 |       C72 |
| ------------------------ | --------: | --------: | --------: |
| 🟢 Полные 48 спутников   | **96.7%** | **98.8%** | **98.9%** |
| 🔴 Только первая очередь |     27.2% |     15.8% |     12.6% |
| 🔴 Отказ 10 спутников    |     79.3% |     81.0% |     82.6% |
| 🔴 ISL ограничен 2000 км |     83.6% |     73.2% |     75.3% |

А целевой показатель:

> **не менее 90% для каждого наземного пункта.**

То есть у задачи уже есть идеальный сюжет.

### Нормальный режим

> Всё хорошо. 97–99% доступности.

### Начинаем развёртывание

> Одной очереди катастрофически недостаточно.

### Выключаем десять аппаратов

> Надёжность падает ниже SLA.

### Ограничиваем дальность межспутниковой связи

> Сеть геометрически видна, но данные до gateway уже не доходят.

Вот это **охрененный материал для пятиминутного питча**.

# А потом на защите делаем шоу

Говорите:

> Сейчас система работает штатно.

**96.7 / 98.8 / 98.9%.**

Кликаете по спутнику:

### `Simulate failure`

Спутник становится красным.

Маршрут прямо на глобусе:

```text
был:

C70 → S18 → S31 → S44 → Gateway

стал:

C70 → S18 → S29 → S41 → Gateway
```

И говорите:

> Сеть автоматически перестроилась, пользователь связи не потерял.

Выключаете критичный аппарат.

BOOM:

### `NO ROUTE`

И не просто красная надпись.

Система пишет:

> Причина: разрыв межспутниковой сети между компонентами.

Вот это жюри **понимает моментально**.

# 4. А ещё можно сделать очень сильную функцию

## «Найти уязвимые спутники»

Для каждого из 48 спутников считаем:

> насколько упадёт availability, если этот аппарат выйдет из строя.

Получаем:

```text
Critical satellites

S31   −8.4%
S14   −6.7%
S26   −5.9%
S48   −4.8%
...
```

На глобусе:

🟢 обычные
🟡 важные
🔴 критические

И говорите:

> Мы не просто визуализируем сеть. Мы определяем аппараты, отказ которых представляет максимальный системный риск.

Это уже звучит как **инженерный инструмент**, а не студенческая демка.

# 5. Следующая killer feature: Configuration Optimizer

Организаторы прямо пишут, что дополнительными возможностями могут быть:

* автоматический подбор конфигурации;
* поиск наиболее уязвимых аппаратов;
* анализ резервных маршрутов;
* сравнение стратегий маршрутизации.

Вот здесь я бы как раз использовал AI-кодинг по полной.

Пользователь нажимает:

### `Optimize configuration`

А backend перебирает / оптимизирует:

* RAAN;
* phase;
* возможно параметры сценария.

Цель:

```text
maximize min(
    availability_C65,
    availability_C70,
    availability_C72
)

minimize max_outage
```

И выдаёт:

> Current worst availability: 79.3%
> Proposed: 82.8%

Даже если невозможно получить 90%, это **не проблема**.

Наоборот:

> В данных условиях достижение SLA 90% невозможно только изменением фазирования. Необходимо изменение архитектуры сети.

Это нормальный инженерный вывод.

# 6. Причём можно делать ещё интереснее

Я немного потыкал предоставленную модель.

Например, при исходной конфигурации и изменении максимальной дальности ISL получается примерно так:

|         ISL | худшая доступность |
| ----------: | -----------------: |
|     2000 км |              73.2% |
|     2200 км |              78.9% |
|     2400 км |              83.9% |
|     2600 км |              87.5% |
|     2675 км |              89.6% |
| **2700 км** |          **90.1%** |
|     2800 км |              96.7% |

То есть можно показать ещё один очень сильный вывод:

> **Для этой архитектуры примерно 2700 км является порогом, после которого все три пункта достигают целевых 90%.**

Вот это уже реальная **decision-support system**.

Не просто:

> «Смотрите, у нас спутники летают».

А:

> **«Вот какой технический параметр нужно обеспечить, чтобы выполнить SLA».**
